### Cycles to break in Rust

- **events ↔ agents:** events imports agents lazily for `normalize`.
- **popover ↔ tray:** popover imports `tray.status` late.
- **settings_api → tray:** settings_api uses `tray.open_path`. Move `open_path` into a small util module.

### Hubs

These are the most imported modules. Give them stable interfaces first.

- **paths:** about 12 importers.
- **events:** 9 importers.
- **usage:** 7 importers.
- **clockapi:** 5 importers.
- **firmware:** 5 importers.

The large leaves are usage (1615 LOC), events (1153) and settings_api (932).

## 2. JS ↔ Python seam

### Settings window

- `ui/index.html` and `ui/app.js` set `api = window.pywebview.api` (`app.js:686`).
- The implementation is `SettingsApi` in `settings_api.py:133`. It is passed as `js_api` in `settings_app.py:123-124`.
- `setup.js` and `preview.js` also share `api`.

JS calls these 33 methods, all defined on `SettingsApi`:

`agents, app_update, app_update_apply, app_update_check, app_update_page, check_update, clawd_pak, disconnect_all, export_backup, factory_reset, finish_setup, fw, import_backup, job, login, open_log, open_web, reboot, save, scan, set_agent, set_agents, set_autostart, set_clock, set_usage_source, setup_clocks, setup_state, setup_use_clock, state, update, usage_preview, usage_sources`

Public Python methods that JS never calls: `preview`, `busy`, `set_hooks`, `close_mdns`.
- `busy` and `close_mdns` are probably used by settings_app.
- pywebview exposes every public method, so these are exposed too.

Python → JS pushes in the settings window (`settings_app.py`):

| Line | Call | Trigger |

### Tray → settings process channel

- Tray spawns `settings_app.command(base, key, tab)` with piped stdin/stdout (`tray.py:461`).
- The child reads `show [tab]` lines from stdin (`settings_app.py:138-152`).
- The tray reads stdout in the `_settings_cmds` thread.

## 5. Concurrency model

**Process model.** The tray process owns the main thread (pystray, which AppKit requires). The settings window is a separate process: pywebview's `webview.start` owns its main thread. The two talk over stdin/stdout pipes, and desktop.json is shared under a file lock.

| Module | Model |
|---|---|
| engine | Thread `clawd-engine` with its own `asyncio.new_event_loop`. `asyncio.Event` stop; `threading.Event` ready. Cross-thread calls go through `call_soon_threadsafe` (engine.py:193-213). Blocking clock reads use `asyncio.to_thread`. `run()` gathers the finder, usage Publisher, EventServer/Brain, BootWatch, `_watch_token` and `_sync_screen` |
| events | Pure asyncio on the engine loop. `Brain.wake` is an `asyncio.Event`. The EventServer uses asyncio streams. Desk push uses `httpx.AsyncClient` |
| usage | asyncio Publisher with `refresh_requested` and `wake` Events. BLE via `ble_loop`. Standalone mode uses `asyncio.run(main())` |
| discovery / bootwatch | discovery has `threading.Lock`s (lines 160, 247) and async `run(stop)`; bootwatch has async `run(stop)` too |
| tray | Daemon threads: `clawd-tray` (refresh every 3 s), `clawd-feed` (first check at 60 s, retry every 1800 s), `clawd-appupdate`, `clawd-agents` (rescan every 600 s), `clawd-settings` (pipe reader), `clawd-restart`, `clawd-rescan`, plus a prompt thread. `threading.Event` stop. On macOS, UI work is marshalled with `AppHelper.callAfter` |
| settings_app | `threading.Lock`; `clawd-settings-in` stdin listener; `clawd-settings-dev` UI watcher |
| settings_api | `_feed_lock` and `_lock` (`threading.Lock`); threads `clawd-feed-check` and `clawd-ota`. pywebview calls the API from worker threads |
| popover | Thread `clawd-pak` fetches the pak, then hands back via `AppHelper.callAfter` |

Cross-process signals:

- `ota.busy` file: makes the engine pause pushes.
- `desktop.json` file lock.
